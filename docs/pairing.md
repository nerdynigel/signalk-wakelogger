# Pairing and credentials

The plugin POSTs `{ "code": "...", "name": "Signal K ..." }` to the configured HTTPS pairing endpoint. A valid response provides a nested device and credentials object containing device ID, required MQTT client ID, username, one-time password, host, port, TLS requirement, telemetry profile, association-status URL and device-scoped association token. Non-production endpoint overrides belong only in local Signal K configuration and must never be committed.

The plugin accepts only HTTPS endpoints, bounded identifiers, DNS hostnames and valid TCP ports. The service should issue codes that are hashed at rest, single-use, account-authorized and expire after ten minutes. Each broker identity must be restricted to publishing its telemetry/state/status/events topics and subscribing only to its acknowledgement topic.

Credentials are stored beneath `app.getDataDirPath()` with directory mode `0700` and file mode `0600`. Rotation should preserve device ID and sequence space. Device replacement creates a new device identity; Wake Logger keeps the current device active until provisioning the replacement succeeds, then revokes and disconnects the old broker client. There is no insecure TLS fallback and production credentials must never be placed in source, plugin configuration, screenshots or logs.

Pairing retries only temporary network, timeout, rate-limit and server failures. It makes at most six attempts with 2, 4, 8, 16 and 30 second delays. An HTTP 400 means the code is invalid or expired and is not retried. If replacement pairing exhausts its retries, the existing credential remains active. Signal K status shows the attempt and delay so the operator can distinguish `Retry pairing` from a rejected code.

The credential record keeps only a SHA-256 fingerprint of the last consumed pairing code. Restarting with that same single-use code does not retry pairing. Supplying a different code explicitly pairs a replacement device and atomically replaces the credential record; the raw pairing code is never copied into credential storage. Outboxes are device-scoped: a replacement starts its own sequence space while the retired device's unacknowledged files remain preserved locally and are never published under the new identity.

Newly provisioned credentials can query their own association state over authenticated outbound HTTPS. After broker authentication fails, the plugin checks that endpoint. A confirmed revocation changes status to `Device revoked — enter a new pairing code` and stops local sampling/transmission; unavailable or inconclusive status checks leave the normal authentication failure intact. Older credentials without this status token remain compatible but cannot distinguish revocation until they pair once again.

Signal K administrators may invoke `POST /plugins/signalk-wakelogger/forget-credentials`. The action closes active transport and removes only `credentials.json`. It records a non-secret retirement tombstone so the consumed code is not replayed, and preserves the installation identity, device-scoped outbox directories, sequence state and diagnostics. The operator must enter a different, fresh pairing code. This local action does not revoke cloud broker access by itself; use Wake Logger's vessel or site-admin revoke workflow when retiring the association.

After the first outbox opens, the credential record is atomically bound to its selected `file` or `database` backend. If credentials survive but the backend marker is later missing or disagrees, startup fails visibly instead of recreating sequence 1 for the same cloud device. A normal upgrade or reinstall with the plugin data directory preserved retains credentials, binding and sequence state. Removing the entire data directory also removes credentials and requires pairing a newly provisioned device identity; selectively restoring credentials without their bound outbox state is intentionally rejected.
